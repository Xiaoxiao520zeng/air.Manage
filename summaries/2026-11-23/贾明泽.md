# 2026-11-23 日总结 · 贾明泽

## 今日完成

1. **明确了今天的目标**：给 Jetson 上 OpenVINS 的**定位坐标突跳**定一套排查方案。目前 OpenVINS 和 RViz 都跑在 Jetson 上，RViz 直接显示板子上的定位结果，中间不经过 Windows。
2. **整理出现象与线索（都还只是线索）**：
   - 此前的记录里提到过，跟踪点数量曾从 **22 个掉到 1 个**，紧接着位置在约 **10 毫秒**内跳了约 **19 厘米**；
   - 但「跟踪点减少」只是**待核实的线索**，不能想当然认定它就是根因——点少可能只是果，也可能是同时发生的另一件事。
3. **定了分层排查的顺序**（从最上游的原始数据往下游显示走，避免一上来就怀疑可视化）：
   1. 对照 **OpenVINS 原始位姿 / 高频里程计 / RViz 显示**三者，找出突跳最早出现在哪一层；
   2. 若**原始位姿稳定、只有 RViz 异常** → 查 Fixed Frame、TF 是否被重复发布、IMU 到相机的坐标变换；
   3. 若**只有高频里程计异常** → 查 IMU 时间戳、快速预测环节、相机与 IMU 的时间偏移；
   4. 若**原始位姿也突跳** → 查双目图像是否拖影/丢帧、左右目是否同步、特征是否骤减、相机与标定配置是否匹配；
   5. 修复后用**同一段录制**对比最大位置跳变与对应时间间隔，并检查相机回到标记位置后的误差。
4. **想通了一个容易误判的点**：原地转动时，朝向变化本身是正常的；如果镜头和 IMU 不在同一点，镜头还会绕 IMU 原点走出**一小段弧线**。所以要判断「这是真定位错误还是坐标变换造成的显示差异」，必须**比较同一个物理参考点**，不然会白折腾。
5. **立了一条原则**：用「自动归零、冻结坐标、平滑轨迹」这类做法**只会把突跳盖住**，看起来好了，根因还在，不能拿它替代真正的定位修复。

## 遇到的问题

- **手上没有证据**：Jetson 的原始消息、rosbag/录制数据都还没拿到，所以「22→1 个点」「10 ms 跳 19 cm」这两个数字只能当线索用，不能当结论。
- **三层数据容易混着看**：原始位姿、高频里程计、RViz 显示分别是三个不同的东西，混在一起看会得出错误结论，必须分开比对才能定位到「第一次出现跳变的那一层」。
- **RViz 本身就有嫌疑**：TF 重复发布、Fixed Frame 设错、IMU→相机外参不对，都能让画面看起来「位置跳了」，但算法其实没跳，容易冤枉 OpenVINS。
- **时间类的坑很隐蔽**：IMU 时间戳和图像时间戳不同步、快速预测用的时间基准不同，表现出来都是「偶发跳一下」，靠肉眼看很难判断，得靠数据。
- **修复效果没法量化**：如果每次只用眼睛看「好像不跳了」，无法证明真的变好，所以必须固定用同一段录制做前后对比。
