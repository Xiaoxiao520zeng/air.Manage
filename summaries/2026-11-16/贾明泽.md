# 2026-11-16 日总结 · 贾明泽

## 今日完成

1. **搞清 ORB-SLAM3 双目模式的原理与边界**：给它 OAK-D Pro 的左右两路画面，处理流程是「找特征点（角点、纹理交界）→ 左右目匹配求视差、结合镜头基线估深度 → 前后帧追踪估计相机位移和转动 → 与地图点联合优化并靠回环修正累计误差」。输出是**相对启动位置的轨迹**（往前走了多少、往左偏了多少），要交给飞控还得自己做坐标系、时间戳和通信对接；它不负责识别挂接杆、判断夹具位置或发电机指令。
2. **搞清 AprilTag 的定位原理**：在画面里找到黑白方形的四个角 → 读内部图案确认是哪张标记 → 用已知真实边长 + 相机标定参数，按四角在画面中的形状和大小算出标记相对相机的位姿 → 再套上实测的「标记中心到挂接点」固定偏移，得到挂接点位置（例如标记贴在挂接点下方 20 cm）。关键是必须用真实尺寸和标定参数，不能只凭画面上看起来多大。
3. **把各方法的职责分开**：无 GPS 时相对起点移动了多少 → ORB-SLAM3；眼前这根已知杆的挂接点在哪 → AprilTag + 实测偏移；前方有没有障碍 → OAK-D Pro 双目深度；飞行姿态保持 → 飞控自身的传感器和控制器。
4. **查了树莓派 5 的可行性**：已有研究在树莓派 5 上跑过 ORB-SLAM3 的 RGB-D 模式，测试序列里完整处理约每帧 **26–62 ms**；但那是特定分辨率、数据集和配置，不能直接当成我们 OAK 双目模式的实测速度。

## 遇到的问题

- **光滑杆特征点少**：窗角、纹理交界这类点才好重复识别，光滑无纹理的杆本身提供不了多少特征点，周围背景反而更重要，SLAM 在这种场景容易跟丢。
- **树莓派 5 的算力还没验证**：最终要同时跑相机采集、目标检测、通信和 SLAM，必须实录总延迟、掉帧、跟踪丢失次数和温度，才能决定要不要换 Orin NX。
- **ORB-SLAM3 只给相对位姿**：不直接给飞控能用的位置估计，坐标对齐、时间戳同步、通信链路都得自己补。
- **AprilTag 有硬限制**：标记被遮挡或移出画面就失去这次测量；挂接最后一小段仍要靠夹具的接触、闭锁反馈；标定不准或偏移量量错会直接带偏结果。

## 附：两种方法的处理步骤

**ORB-SLAM3（双目）**

1. 找特征点：在画面里寻找窗角、纹理交界等容易再次认出的点。
2. 匹配左右画面：找同一个特征点在左右画面的位置差，结合两镜头间已知距离估计该点有多远。
3. 追踪前后画面：相机移动后再找这些点出现在哪里，据此估计相机移动和转动了多少。
4. 反复校正：同时调整相机轨迹和地图点位置让预测与实际尽量对齐；再次经过认识的地方时，用「认出了旧地点」修正累计误差。

**AprilTag**

1. 在画面中找到黑白方形，确定四个角。
2. 读取内部图案，知道看见的是哪一张标记。
3. 已知标记实际边长和相机参数，根据四角在画面中的形状与大小，算出标记相对相机的距离和方向。
4. 用「标记到挂接点」的固定偏移，算出挂接点相对相机的位置。
