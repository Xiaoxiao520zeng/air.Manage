## 今日完成

- 解决了 Ubuntu 下串口打不开的问题。现象是设备能枚举、`/dev/ttyUSB0` 确实存在，但程序一打开就报 `Permission denied`——定位下来不是驱动没装，而是当前用户不在 `dialout` 组。
- 用 `sudo usermod -aG dialout $USER` 把用户加进 `dialout` 组，重新登录后用 `id` 确认组成员已生效，串口读写恢复正常。
- 顺带排查并处理了两个「抢串口」的隐形占用：Ubuntu 默认在跑的 **ModemManager** 会自动探测新插入的串口设备、往里发 AT 指令，造成通信中途数据被吞；**brltty** 会把 CH340 这类 USB 转串口设备误认成盲文点显器直接接管，导致设备刚出现就消失。分别用 `systemctl disable --now ModemManager` 和停用 brltty 处理掉。
- 整理出一套固定排查顺序：先看设备有没有枚举 → 再看权限与所属组 → 再看谁在占用 → 最后才怀疑波特率和接线。以前习惯一上来就重装驱动，其实顺序反了。
- 记录了必须避开的两条弯路：`chmod 777` 临时放开权限既不持久也不安全；没确认占用之前就重装驱动基本等于白折腾。
- 整理成一份排查笔记（全文见文末「附：Linux 串口权限与占用排查笔记」）。

## 附：Linux 串口权限与占用排查笔记

### 一、现象

| 现象 | 容易误判成 | 实际常见原因 |
| --- | --- | --- |
| `Permission denied` | 驱动坏了 | 用户不在 `dialout` 组 |
| 设备插入后出现又消失 | 硬件接触不良 | brltty 抢占了 CH340 |
| 能打开但收发没数据 | 波特率配错 | ModemManager 在探测设备 |
| 上一条命令能通、下一条报 `Device busy` | 驱动不稳定 | 上一个进程没退出，端口还占着 |

### 二、权限为什么卡住

Linux 把串口设备当成设备节点，权限是 `root:dialout`、`660`：

```text
crw-rw---- 1 root dialout 188, 0 11月 10 20:15 /dev/ttyUSB0
```

意思是只有 root 和 `dialout` 组的成员能读写。普通用户默认不在这个组里，所以「驱动正常、设备也在、就是打不开」。

解决办法：

```bash
sudo usermod -aG dialout $USER   # 加入 dialout 组
```

关键在于**必须重新登录**才会生效。原因：用户的组成员身份是在登录时写进会话的，改 `/etc/group` 不会反过来更新已经存在的会话。临时验证可以用 `newgrp dialout`，但它只作用于当前 shell。

验证是否生效：

```bash
id          # 输出里应该能看到 dialout
ls -l /dev/ttyUSB0
```

### 三、三个「抢串口」的元凶

1. **ModemManager**
   Ubuntu 桌面版默认安装，专门管 3G/4G 模块。它会周期性扫描所有新出现的串口设备并发送 AT 指令「问一句这是不是调制解调器」，而你的设备会被这些指令打断，表现为数据偶发丢失、通信时好时坏。

   ```bash
   sudo systemctl disable --now ModemManager
   ```

2. **brltty**
   盲文点显器服务。它有个已知问题：会把 CH340 芯片的 USB 转串口识别成盲文设备并加载驱动，结果设备刚枚举就被抢走。表现出来就是「插上去闪一下就没了」。

   ```bash
   sudo systemctl stop brltty
   sudo systemctl disable brltty
   # 或者直接卸载：sudo apt remove brltty
   ```

3. **没退出的旧进程**
   串口是独占资源。`screen`、`miniterm`、串口监视器窗口、上一次跑崩的脚本，只要还活着，端口就一直被占着。

   ```bash
   sudo lsof /dev/ttyUSB0
   sudo fuser -v /dev/ttyUSB0
   ```

### 四、排查顺序

按这个顺序走，基本不会绕路：

```text
1. 设备枚举了吗？        lsusb / dmesg | tail -20
2. 设备节点在吗？        ls /dev/ttyUSB* /dev/ttyACM*
3. 权限对不对？          ls -l + id
4. 谁在占用？            lsof / fuser
5. 系统服务在抢吗？      systemctl status ModemManager brltty
6. 才开始怀疑通信参数    波特率 / 数据位 / 校验位 / 停止位 / TX-RX 交叉 / 共地
```

前五步都发生在「物理层之上、应用层之下」，把这几层排除干净，再去调波特率才有意义。

### 五、固定设备名（避免设备号跳变）

插不同的串口设备时，`ttyUSB0` / `ttyUSB1` 的顺序会变，程序里写死设备名迟早出问题。用 udev 规则按芯片序列号固定：

```bash
# 先查设备的 VID/PID 和序列号
udevadm info -a -n /dev/ttyUSB0 | grep -E "idVendor|idProduct|serial"

# /etc/udev/rules.d/99-gimbal.rules
SUBSYSTEM=="tty", ATTRS{idVendor}=="1a86", ATTRS{idProduct}=="7523", ATTRS{serial}=="XXXX", SYMLINK+="ttyUSB_gimbal"
```

```bash
sudo udevadm control --reload-rules && sudo udevadm trigger
```

之后程序统一打开 `/dev/ttyUSB_gimbal`，插拔顺序怎么变都不受影响。

### 六、本次小结

这次问题的本质是**权限模型**，不是驱动：设备节点属于 `dialout` 组，用户不在组里就无权读写；而组的变更要重新登录才进会话。

另外两个坑都不在「驱动」这个方向上：ModemManager 会主动探测串口设备发 AT 指令，brltty 会误抢 CH340。真正的排查顺序应该是「枚举 → 权限 → 占用 → 服务 → 参数」，一上来重装驱动是最没效率的一条路。
